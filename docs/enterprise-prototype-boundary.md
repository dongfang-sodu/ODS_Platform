# 企业原型边界与实施记录

最后更新：2026-08-06。

## 两层目标

ODS 的后续建设明确分为两层，论文不得混用两层结论。

| 层次 | 目标 | 可使用的表述 |
| --- | --- | --- |
| 论文原型实际实现 | 单台 2 核 CPU、4 GB 内存、60 GB SSD 云服务器；单节点 K3s；最高 50 名轻量并发用户 | “本文实现并验证” |
| 小型企业推荐部署 | 2000 名注册用户、1000 名峰值在线用户；跨可用区多节点；一年最多一次且不超过 30 分钟的失效 | “企业部署时建议采用” |

单机中运行多个副本只能验证软件切换流程，不能证明具备主机级高可用能力。企业推荐部署使用 3 个 Kubernetes 工作节点、3 台独立 PostgreSQL 服务器、高可用 Redis/RabbitMQ 和外部 S3 兼容对象存储。

## 已实现基础能力

- 访问令牌有效期默认为 15 分钟，刷新令牌有效期默认为 8 小时。
- 刷新令牌每次使用后轮换，数据库只保存 SHA-256 哈希。
- 用户退出、修改密码或管理员禁用账号后可以撤销会话。
- 用户可以在账号安全页面查看仍有效的登录会话，并单独注销某个会话。
- 连续 5 次登录失败后锁定账号 3 分钟。
- 密码重置令牌有效期为 15 分钟且只能使用一次；接口不泄露邮箱是否存在。
- 密码至少 12 位，必须同时包含大写字母、小写字母、数字和特殊字符。
- Nginx 对普通 API 和登录接口分别限流。
- Prometheus 格式基础指标已开放，健康探针可供容器平台使用。
- Docker Compose 已包含 PostgreSQL、Redis、RabbitMQ、后端和前端。
- `deploy/k8s` 已提供按 2 核 4 GB 环境限额的单节点 K3s 发布骨架。
- GitHub Actions 已提供自动测试、前端构建、容器构建和手工触发镜像发布。

## 尚未实现或尚未实测

- Redis 缓存策略、缓存穿透/击穿保护尚未接入业务查询。
- RabbitMQ 可靠消息、重试、死信队列和消费者负载均衡尚未接入业务任务。
- S3 分片上传、文件校验、缩略图生成和权限签名地址尚未实现。
- 组织、部门、项目成员和数据范围授权尚未形成完整闭环。
- 审批、采购价格、归档删除、全局搜索、报表和站内告警仍需开发。
- 当前机器没有 Docker 和 kubectl，因此 Compose 与 K3s 配置只完成静态 YAML 解析，尚未真实启动。
- PostgreSQL V4 迁移断言已加入 Testcontainers 用例，但当前机器没有 Docker，该用例仍会跳过。
- 原型前端将访问令牌和刷新令牌保存在浏览器 `localStorage` 以保持实现简单；企业部署建议改为短时访问令牌配合安全的 HttpOnly、Secure、SameSite Cookie，并增加设备级风控。

## 原型压测边界

压测程序从另一台电脑运行，按 10、20、30、50 名并发用户逐级测试登录、普通查询、工件保存和工单提交。视频缩略图、批量导入、深度追溯和大型报表仅验证后台排队、完成与失败重试。每组测试预热后运行 5 至 10 分钟并至少重复 3 次，记录吞吐量、平均响应时间、95% 响应时间、错误率、CPU、内存和数据库连接数。

该结果只说明受限单节点环境的基本并发能力，不用于线性推算企业 1000 人并发容量。
